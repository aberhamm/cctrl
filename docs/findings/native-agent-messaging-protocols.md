# Claude Code and Codex messaging protocols

Investigated 2026-11-16. These are version-pinned findings for cctrl bridge
design, not a declaration that undocumented provider interfaces are stable.
No runtime adapter was changed by this investigation.

Claude Code exposes a local protocol for independently launched sessions.
Codex's native subagent mailbox belongs to a runtime's agent tree; external
clients use App Server or desktop host tools. cctrl already has a durable
mailbox and notification adapters for both providers. Completing native
request/reply needs more than writing a prompt to either transport.

## Protocol map

| Surface | Transport and addressing | Boundary |
|---|---|---|
| Claude independent sessions | UTF-8 JSONL; Unix socket on macOS/Linux, named pipe on Windows; registry-selected endpoint | Local cross-session input, status notifications, and replies |
| Claude teammates | Locked JSON-array inbox files, or a storage-provider path | Team mailbox; separate from the independent-session socket |
| Codex collaboration | Rust calls, operation queues, and an in-memory mailbox; runtime registry IDs/agent paths | Root agent and its subagents, not an external process mailbox |
| Codex App Server | JSON-RPC-style requests over supported stdio/Unix/WebSocket transports; thread IDs | External thread/turn input through the owning server |
| Codex desktop app tools | Length-prefixed JSON-RPC 2.0 over a local pipe; dynamic host tool calls | Desktop cross-chat tools, separate from App Server |
| cctrl peers | Durable JSONL mailbox and per-peer stdio MCP; canonical peer names | Common receive/reply/handling-ACK contract across runtimes |

## Claude independent-session protocol

### Discovery and framing

Use `messagingSocketPath` from the selected process's session registry,
ordinarily `~/.claude/sessions/<pid>.json`. The registry advertises
`peerProtocol: 1` and features including `notify_idle`,
`reply_across_default_dirs`, and `artifact_yield`.

The normal socket location is
`(XDG_RUNTIME_DIR || Claude temporary directory)/cc-socks/<pid>.sock`, with a
long-path fallback under `/tmp/cc-socks-<uid>/`. These are descriptive defaults:
custom paths, moved-aside sockets, and process reuse mean PID-derived paths are
not sufficient endpoint identity.

Each native frame is UTF-8 JSON followed by a newline. A normal send has this
shape; placeholders are illustrative, not usable credentials or endpoints:

```json
{"type":"auth","token":"<recipient peer token>"}
{"msgV":1,"msg_id":"<uuid>","type":"user","message":{"role":"user","content":"<cross-session-message from=\"uds:/sender.sock\" from-name=\"bridge\" from-mode=\"prompting\">\nHello\n</cross-session-message>"},"priority":"next","from":"uds:/sender.sock"}
```

- `message.content` is a nonempty string, not a content-block array.
- `msgV: 1` and `msg_id` provide native envelope version and correlation.
- `from` is the reverse address. Native sender addresses use `uds:` plus the
  encoded socket path.
- Normal sends use `priority: "next"`; the receiver also handles `"now"`.
- Optional `session_id` must match the receiving conversation when supplied.
- Optional `uuid` is preserved only through explicit
  `--messaging-socket-path`; otherwise the receiver generates its transcript ID.
- The XML envelope also supports `from-session`, `hop-chain`, and `from-plugin`.
  File attachments follow a separate materialization path not covered here.

### Authentication, identity, and admission

The first frame can authenticate with the recipient's peer token. Authentication
is optional by default on macOS/Linux and required by default on Windows in
this build. Peer token metadata is published in a mode-`0600` file:

```text
~/.claude/sessions/<pid>.<sha256(canonical_socket_address)>.key
```

The metadata includes `peerToken` and may include process-start and PID-domain
information. The separately minted child token is inherited through
`CLAUDE_CODE_MESSAGING_TOKEN`; it is not interchangeable with the peer token.
No actual token values were collected in the findings.

Native endpoint checks include process identity where available, peer ownership,
and rejection of symlink reply targets. The receiver records verified process
identity separately from the claimed `from`. Sender labels and permission-mode
assertions must not be treated as authenticated authority.

For a normal user frame, the receiver obtains the sender's permission class
from **`from-mode` inside the XML content**, not a top-level `from_mode` JSON
property. Some control frames use the top-level property instead.

| Claimed sender class | Prompting recipient | Bypass recipient |
|---|---|---|
| `prompting` | Accept by default | Hold by default |
| `bypass` | Hold by default | Accept by default |
| Missing | Accept by default | Hold by default |

Explicit `crossSessionInbound: "accept" | "hold" | "refuse"` settings can
override this default; repository settings may tighten broader settings. Unknown
recipient mode holds messages, and feature gates can refuse reception. Other
admission controls include rate, duplicate, loop, and capacity checks. The held
queue is bounded at 100 entries in this build.

A bridge must represent its real provenance and authority. Adding a bypass
assertion merely to avoid a hold would not establish bypass authority.

### Receipts, replies, and idle notifications

The native sender does not consume a synchronous delivery ACK on the sending
connection. Successful write completion establishes neither model delivery nor
handling. Status messages return over a **new connection to the vetted `from`
address**, correlated by `orig_msg_id`:

```json
{"type":"control","action":"peer_message_status","status":"delivered","orig_msg_id":"<original uuid>","from":"uds:/recipient.sock","msgV":1,"msg_id":"<receipt uuid>"}
```

Observed status vocabulary is `held`, `denied`, `expired`, `delivered`,
`refused`, and `dropped`. Refusal can also be encoded as `status: "expired"`
with `status_detail: "refused"`. Dropped receipts may include `drop_reason`
and `dropped_msg_ids`. A native `delivered` receipt still is not a cctrl
handling ACK.

Claude can reply with `SendMessage` to the sender address. A complete bridge
therefore needs a persistent inbound endpoint, verified routing ownership, and
mapping to the actual cctrl recipient. Arbitrary callback paths are not
automatically accepted: socket namespace and cross-default-directory reply
checks apply.

Idle subscription is a separate control operation:

```json
{"type":"control","action":"notify_when_idle","from":"uds:/sender.sock","msg_id":"<uuid>","from_mode":"prompting","msgV":1}
```

The reverse response uses `action: "peer_idle_notice"`, `orig_msg_id`,
`state`, and optional `finished_at`/`detail`. It is not a chat reply or a
handling acknowledgement.

### Teammates and tool routing

The disk teammate inbox is
`~/.claude/teams/<sanitized-team>/inboxes/<sanitized-agent>.json`. It contains
a JSON **array**, not JSONL. Entries require `from`, `text`, and `timestamp`;
optional fields include `type`, `read`, `color`, `summary`, `from_plugin`, and
native identity/signature metadata. Writers lock, append, and atomically
rewrite; current code also supports storage providers.

An in-memory provenance ledger, optional Ed25519 lead-entry signatures, and
replay/unverifiable-message handling mean direct inbox editing is not equivalent
to native delivery. The independent-session socket is the relevant cctrl bridge
boundary.

`SendMessage` multiplexes main/subagent, teammate, independent-session, and
remote routes. This build's general tool input uses `to`, `message`, optional
`summary`, and optional `notify_when_idle`; historical `type/recipient/content`
examples should not establish its current schema. Cross-machine Remote Control
and cloud routes are distinct from the local socket and were not investigated
at their wire boundary.

## Codex protocols

### Internal collaboration

The version-matched release implements `send_message({target,message})` as
`QueueOnly` and `followup_task({target,message})` as `TriggerTurn`. Both require
known caller and recipient entries in the local runtime registry; a followup
cannot target the root. Addresses can be UUID thread IDs or relative/canonical
agent paths such as `/root/worker`.

`LocalAgentRuntime` shares an in-memory
`Mutex<Option<HashMap<ThreadId, Mailbox>>>` and Tokio watch notifications with
its agent tree. Messages also enter loaded-session operation queues. There is
no external mailbox file or global socket in this implementation for an
independently launched process to join.

The internal `InterAgentCommunication` envelope includes `author`, `recipient`,
`other_recipients`, `content`, and `trigger_turn`, with optional ID, encrypted
content, and internal metadata. Context rendering produces `Message Type`,
`Task name`, `Sender`, and `Payload` text. Copying that text into a user prompt
does not reproduce native identity, routing, or delivery.

### External App Server

The installed binary generated an experimental `ClientRequest` schema with 180
methods. It includes `turn/start` and `turn/steer`, but no native inter-agent
message request. The external input sequence is:

```json
{"id":1,"method":"initialize","params":{"clientInfo":{"name":"cctrl","version":"1"},"capabilities":{}}}
{"method":"initialized","params":{}}
{"id":2,"method":"thread/read","params":{"threadId":"THREAD","includeTurns":false}}
{"id":3,"method":"turn/start","params":{"threadId":"THREAD","input":[{"type":"text","text":"Message"}]}}
```

Resume an unloaded eligible thread through `thread/resume` before submitting
input. Steering an active turn requires **`expectedTurnId`**, not `turnId`:

```json
{"id":4,"method":"turn/steer","params":{"threadId":"THREAD","expectedTurnId":"TURN","input":[{"type":"text","text":"Follow-up"}]}}
```

Both input methods expose optional `clientUserMessageId`; its presence alone
does not establish idempotency semantics. cctrl's existing adapter emits the
RPC envelopes above without a `jsonrpc` property.

CLI help advertises stdio, Unix-socket, and WebSocket listener modes.
WebSocket authentication supports capability-token and signed-bearer-token
modes. A newly started standalone server is not automatically the owner of a
thread already running in another CLI process. Use the existing owning server
and preserve writer-lock/ownership checks; never open a second writer just to
deliver input. See the [task lifecycle contract](codex-task-lifecycle-contract.md).

### Desktop app-tools pipe

The shipped app-tools bridge gets its endpoint from
`CODEX_APP_TOOLS_PIPE_PATH`. Each frame is a four-byte unsigned little-endian
payload length followed by that many bytes of UTF-8 JSON-RPC 2.0. The bridge
caps payloads at 8 MiB.

It requests dynamic definitions with `tools/list` and forwards calls through
`tools/call`; cancellation uses `tools/cancel`. Forwarded metadata includes
namespace, caller source, caller thread/turn/call IDs, and host identity where
applicable. `send_message_to_thread` appears in the delegation tool set, but
the host supplies its definition and handler. That name in the bundle does not
establish availability in every session. This investigation did not inspect
the host handler's delivery or ownership semantics.

This pipe is separate from both the App Server API and the internal agent-tree
mailbox. Their framing and initialization are not interchangeable.

## Existing cctrl behavior and bridge gaps

The implementation anchors below describe the investigated cctrl commit:

| Owner | Existing behavior | Remaining gap |
|---|---|---|
| `cctrl` peer mailbox | Durable `messages.jsonl`, canonical peer identity, receive/reply/ACK lifecycle | Keep this as the common record; native transport acceptance is not handling |
| `cctrl` Claude socket delivery | Finds `.messagingSocketPath`; sends a simple `type:user` frame; prompting-mode gate and tmux fallback | Does not provide the full native envelope, a reply endpoint, or native receipt correlation |
| `hooks/native-send-log.py` | Records native `SendMessage` metadata and keyed body fingerprints | Intentionally excludes bodies; cannot ingest or reconstruct native replies |
| `lib/codex_app_server.py` and `lib/codex_websocket.py` | Existing daemon via `codex app-server proxy`, HTTP Upgrade, RFC 6455 framing, initialize/initialized | External thread-input channel, not native collaboration membership |
| `lib/codex_peer_delivery.py` | Checks exact thread/cwd, ownership, version, archive/busy state; persists attempt receipts before `turn/start` | Sends mailbox notifications; busy tasks defer and app inline delivery is unsupported |
| `lib/peer_mcp.py` | Per-peer stdio MCP interface to the common mailbox | Common tools remain the receive/handling-ACK boundary across providers |

The current Claude socket frame is:

```json
{"type":"user","message":{"role":"user","content":"<mailbox notification>"}}
```

Its missing permission class explains why the adapter avoids bypass/unknown
recipients. Restoring a class field would not by itself establish delivery or
sender authority.

Codex notifications carry a `[cctrl-delivery:<attempt-id>]` marker. Persisted
receipts and user-message history reconcile ambiguous submissions; a lost
response must not cause blind replay. The server has no atomic start-only-if-idle
operation, so a preflight idle check can race with new app input. Existing
observed busy state defers; strict ordering is not guaranteed.

The bridge direction supported by this evidence is:

1. Keep canonical cctrl message IDs, sender identity, and queued/delivered/ACK
   states authoritative.
2. Resolve the runtime endpoint with fresh session/process or thread/owner
   evidence.
3. Deliver an ID-bearing notification through the relevant adapter.
4. For Claude native replies, own a vetted persistent callback endpoint and
   translate reply/status correlation into cctrl records without treating
   claimed native identity as authority.
5. Have the recipient use cctrl MCP/CLI to receive, reply, and ACK handled work.
   Preserve held, refused, deferred, and ambiguous outcomes separately.

These are design implications, not implemented capabilities or an integration
approval. Follow the [peer contract](../../AGENTS.md#peer-messaging): native
messages carry pings and low-stakes notes; approvals, decisions, tasking,
handoffs, and ACK-requiring work belong in the durable mailbox.

## Refreshing the findings

Refresh artifact identity and schema before relying on undocumented fields in
a new provider build. The non-delivery Codex checks used here are:

```sh
codex --version
codex app-server --help
codex app-server generate-json-schema --experimental --out <new-scratch-directory>
cctrl codex capabilities --json
```

For Claude, preserve each extracted chunk's original byte offset, byte length,
and SHA-256 plus the executable's identity. Analyze it as inert text. Do not
substitute a third-party recovered source tree or historical team schema for
the installed build. No bundled code or credential files need to be committed
to cctrl to record these findings.

Future compatibility verification still needs isolated end-to-end tests for
authentication, permission-class admission, callback vetting, status/refusal
correlation, duplicate/reconnect handling, shutdown, idle wakeup, and a full
Claude-to-Codex reply/ACK round trip. Existing-session delivery was intentionally
outside this read-only investigation.
