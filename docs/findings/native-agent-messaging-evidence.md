## Subsequent native bridge verification

An isolated smoke on the installed Claude Code `2.1.325` used only a newly
spawned test Claude session and a bridge-owned endpoint. The native listener
accepted a bridge frame, emitted the native cross-session peer input, and
started a second turn. This establishes installed-Claude native ingress and
turn wakeup for that tested configuration, beyond mere successful socket write.
The test record reported no endpoint errors and no timeout.

The spawned session's expired authentication prevented model execution: both
turns returned an authentication error. Native model-driven `ListAgents` /
`SendMessage`, an outbound reply, and a complete Claude/Codex model round trip
were unverified in that smoke. The retained private `live-smoke/result-transport.json`
records ingress and the authentication limitation; no private session content,
credentials, or machine-specific paths are included here.

A subsequent installed-Codex `0.167.0` smoke used one newly created test thread.
`thread/queue/add` accepted its input, thread history contained the exact
`userMessage.clientId` matching the submitted correlation ID, and a completed
model turn returned the expected test token. The native queue was consumed
(`queue_remaining: 0`). The exact owned test thread was archived afterward;
existing sessions were not messaged. The retained private queue-smoke result
records these observations without publishing local paths or session contents.

This verifies native queue submission, correlation, consumption, and model
execution in that tested Codex server configuration. It does not establish all
independently running CLI/extension configurations or a full Claude↔Codex
model-driven reply/ACK round trip. The later test below establishes that narrower
cross-provider claim.

### Live bidirectional reply and receipt test

A later test on 2026-11-16 passed with actual Claude Code `2.1.325` and Codex
`0.167.0` model sessions, using the installed cctrl native bridge:

| Direction | Verified behavior |
|---|---|
| Claude → Codex | Claude used native `SendMessage` to the exact Codex bridge endpoint; Codex consumed the input, explicitly ACKed it, and sent a correlated reply |
| Codex → Claude | Codex initiated a native bridge send; Claude consumed native peer input, explicitly ACKed it through cctrl MCP, and sent a correlated reply |
| Reply handling | Each original sender explicitly ACKed the reply's own message ID; both `reply_to` links matched their original requests |
| Receipts | All four explicit ACK notifications reached the corresponding sender's provider input, identified by the original message ID |
| Duplicate and cleanup checks | Exactly four message records and four receipt attempts remained; all four messages were acknowledged, test endpoints/sockets were removed, and the owned Codex test chat was archived |

Claude used its normal default/prompting admission mode and the actual native
`SendMessage` and cctrl MCP tools. The owned Codex test chat used a custom tool
handler bound to that exact thread to invoke installed bridge commands. The
test did not resume another writer, message existing sessions, override native
admission, or copy authentication tokens. No duplicate or fallback send occurred.

The background execution context initially saw an expired credential fallback
even after interactive login succeeded. Launching the test in the user's
existing macOS GUI session made the valid Keychain login visible. Keychain
permissions and credential contents were not changed. An expired background
fallback alone therefore does not prove the interactive login is invalid.

The retained private `run-47e2e5f32c/result.json` contains provider events,
correlation checks, and cleanup results; its `bridge-evidence` directory retains
the test ledger. The test used native Codex events because immediate full turn
history reads returned `list_turns is not supported yet` in this configuration.

Isolated Claude adapter, Codex queue, bridge-ledger, and subprocess tests cover
the implemented boundaries. A simulated two-direction bridge integration tests
routing and reply/ACK plumbing; it does not establish real-provider model
behavior. Read the executed test results for the current counts and scope rather
than treating this evidence baseline as an evergreen test total.

The current native endpoint implementation supports POSIX peer verification.
Windows bridge operation fails closed when OS peer verification is unavailable;
the source-derived Windows wire reference is not a Windows support claim.
Native bridge discovery and IPC are local; no network messaging bridge is exposed.

## Steer probes (P0 and P0b)

Two live probes measured `turn/steer` on codex-cli 0.167.0 against the shared
app-server daemon. Facts and ids only; no message bodies. Both ran on the
Studio on the dates shown; every mutation was guarded by an identity check
(thread id, cwd, preview nonce) and aimed only at the probe's own thread.

**P0 (2026-11-18): a cctrl tmux Codex is not loaded in the daemon.**

- Throwaway: a cctrl-launched Codex tmux session, thread
  `01a1f087-92a0-7502-bf93-27a01b202ca7`, started with `-a on-request -s read-only`.
- The TUI ran with no `--remote` and no app-server child. `CCTRL_CODEX_REMOTE_DEFAULT`
  was unset.
- Daemon `thread/loaded/list`: 22 threads, the probe absent while it was mid-turn.
  `thread/read`: `status notLoaded`, `canAcceptDirectInput null`, `source cli`.
- All 22 loaded threads (status fields only): `source vscode` (app) threads reported
  `canAcceptDirectInput true`; `source subAgent` threads reported `false`; none were
  cctrl tmux threads.
- For the TUI thread, `thread/turns/list` and `thread/read includeTurns:true` both
  labelled its running turn `01a1f087-93fc-7f13-8692-1c2950e9df06` as `interrupted`
  (completedAt null), so neither shows an `inProgress` turn there.
- One `turn/steer` into that thread: JSON-RPC `-32600`, `thread not found: <thread id>`.
  The thread stayed unloaded and the test string never appeared in the pane.
- Verdict: REPLAN; steer scope became loaded app threads only. Cleanup: session closed,
  no bridge endpoint, scratch dir removed.

**P0b (2026-11-19): errors, turn-id source and the approval wait.**

- Throwaway: an app-owned Codex thread from `cctrl start --agent codex --app-owned`,
  thread `01a1f158-9725-7f23-8178-d5f1cc1d360a`, in a `mktemp -d` scratch directory.
  It was in `thread/loaded/list`, reported `canAcceptDirectInput true`, and was
  archived at the end.
- Calls on the thread: 5 `turn/steer`, 4 `turn/start`, 3 `turn/interrupt`, 1 `thread/archive`.
  No other thread was read beyond loaded-list membership.
- Errors (all code `-32600`): `no active turn to steer` (idle thread, nothing committed);
  ``expected active turn id `A` but found `B` `` for a stale id and for an all-zero id
  (nothing committed); `thread not found: <id>` (from P0).
- A matching steer (turn `01a1f159-50b2-7023-b238-c48e4e6a0d90`) returned that turn id
  and appeared as a second `userMessage` in the same turn with `clientId` equal to the
  `clientUserMessageId` sent (`p0b-ok`); no new turn, empty queue.
- Waiting on approval (turn `01a1f15d-0ba5-7681-a7f0-4fa2c25cee03`, status
  `active` with `activeFlags [waitingOnApproval]`): `turn/steer` returned success with
  that turn id, status stayed flagged, and after `turn/interrupt` about 3 s later the steer's
  nonce count was 0 across all turns and the queue was empty. The steer was accepted and
  dropped.
- `thread/turns/list {limit:1, sortDirection:desc, itemsView:notLoaded}` 2.4 s after
  `turn/start` returned the same turn id as `turn/start` with `inProgress`; it later reported
  `completed` and `interrupted` correctly.
- The turn-starting connection received no approval request; only `thread/status/changed`
  notifications.
- Cleanup: `thread/archive` returned `{}`; the thread left `thread/list` and
  `thread/loaded/list`, and `app-ls --all` shows it `archived`. No bridge endpoint; scratch dir removed.
- Verdict: GO, with the amendments now in the design: the client checks `activeFlags`
  itself, classifies errors by message text, and confirms a steer by `clientId`.

## Refreshing the findings

Refresh artifact identity and schema before relying on undocumented fields in
a new provider build. The non-delivery Codex checks used here are:

```sh
codex --version
codex app-server --help
codex app-server generate-json-schema --experimental --out <new-scratch-directory>
cctrl codex capabilities --json
```

For Claude, preserve each extracted chunk's original byte offset, byte length,
and SHA-256 plus the executable's identity. Analyze it as inert text. Do not
substitute a third-party recovered source tree or historical team schema for
the installed build. No bundled code or credential files need to be committed
to cctrl to record these findings.

The live test establishes normal-admission bidirectional model replies and
explicit ACK receipts for the tested provider builds. It does not establish
every independent CLI/extension configuration, held/refused admission behavior,
Windows support, or every lifecycle/authentication variant. Those need separate
real-provider coverage; isolated module tests do not establish them. Existing
user sessions were not delivery targets for this investigation.
